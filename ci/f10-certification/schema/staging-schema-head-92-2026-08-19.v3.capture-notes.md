## Phase 1 — parse

`v2.sql` was parsed programmatically (Python, not hand-sliced) into typed statement objects: `CREATE TABLE`, `ALTER TABLE ADD CONSTRAINT` (sub-classified PK / UNIQUE / CHECK / FK by keyword), `CREATE [UNIQUE] INDEX`, `CREATE OR REPLACE FUNCTION`, `CREATE [CONSTRAINT] TRIGGER`, `INSERT INTO`. The first parser attempt undercounted objects (16 tables, 27 functions, 18 triggers, 0 inserts) because its function-block terminator only recognized a *lone* `$function$` closing line; several bodies close with `END $function$` on one line (no line break), which caused the parser to swallow everything up to the *next* lone `$function$` — silently merging several tables/triggers/inserts into a wrongly-attributed function body. Fixed by detecting the closer as any line containing `$function$` that isn't the `AS $function$` opener. Re-run found the true counts: **20 tables, 157 constraints (20 PK/8 UNIQUE/96 CHECK/33 FK), 54 indexes, 21 triggers, 37 functions, 3 seed inserts** — cross-checked against independent `grep -c` counts on the raw file, exact match.

## Phase 2 — table/FK two-pass rewrite

V2's SQL already separates `CREATE TABLE` (bare columns) from `ALTER TABLE ADD CONSTRAINT` (no inline FKs at all) — so no FK-extraction-from-inline-columns was needed, only reordering. Design:

- **Pass A** — all 20 bare `CREATE TABLE` (any order; zero inter-table dependency since there are no inline FKs).
- **Pass B1** — all 28 `PRIMARY KEY`/`UNIQUE` constraints (needs Pass A only).
- **Pass B2** — all 96 `CHECK` constraints (row-local by construction — Postgres disallows subqueries in CHECK — needs Pass A only, placed here for clean grouping).
- **Pass B3** — all 33 `FOREIGN KEY` constraints (needs Pass A + Pass B1: every FK target column-set must already carry a PK/UNIQUE).

A verification pass cross-referenced every one of the 33 FK constraints' `(target_table, target_columns)` against the full set of Pass-B1 PK/UNIQUE column-sets per table: **0 unresolvable targets**. This included direct confirmation of the exact circular pair — `manual_giros.assigned_actor → auth_actors(actor)` and `auth_actors.active_manual_giro_id → manual_giros(id)` — both nullable, both trivially resolved by Pass A creating both tables before Pass B3 adds either FK (no deferred constraints, no `NOT VALID` needed). No semantic mismatch found on any relocated FK (name/columns/target/actions all copied byte-identical, only moved).

## Phase 3 — identity/sequence

`clientes.id`'s `GENERATED BY DEFAULT AS IDENTITY (START WITH 1 INCREMENT BY 1 MINVALUE 1 MAXVALUE 9223372036854775807 CACHE 1 NO CYCLE)` clause — already fully specified in V2 SECTION 8 as a *comment*, never live SQL — is now applied inline in Pass A's `CREATE TABLE clientes`, exactly matching the form V2's own comment prescribed for "a fresh from-scratch build." No separate freestanding `CREATE SEQUENCE` — the inline identity clause lets Postgres create and own `clientes_id_seq` itself, matching the captured `OWNED BY` semantics precisely. This is the one of two disclosed content changes (see `v3.metadata.json`).

## Phase 4 — post-table object order

Confirmed (general Postgres behavior, not V2-specific): `CREATE FUNCTION`/`CREATE OR REPLACE FUNCTION` never validates referenced tables/functions at creation time (lazy binding, even for `LANGUAGE sql`) — functions can be created in any order relative to tables and each other. The only hard ordering requirement is **tables + functions before the triggers that reference them**, which the pass order (A→B→C→D→E) already satisfies. No `CREATE EXTENSION` needed: `gen_random_uuid()` (used as every UUID PK's default) is a PostgreSQL-17 built-in since PG13 — reconfirmed by re-grepping all 37 function bodies for any extension-only call (`uuid_generate_v4`, PostGIS, `pg_trgm`, etc.): zero matches.
